# 심의위원회 RAG V3 적용 및 검증

## 현재 구현

- 문서 자료실: `/committee/documents`.
- 관리자: `/manage`의 AI 관리 및 기존 청킹 영역에서 자료실을 제공한다.
- 원본 목록 전체 탐색, 게시물별 모든 첨부 목록 등록, 본문 길이 제한 제거.
- PDF를 페이지별로 Gemini에 전달하여 제목·문단·표 구조를 추출한다. 표의 headers/rows를 DB에 저장하고 원문 마크다운 표로 표시한다.
- 이미지 페이지, 누락 의심 숫자, 판독 불가 영역은 검토 상태로 보류한다. 관리자가 PDF와 대조 후 승인하거나 페이지 OCR을 재실행한다.
- 청크를 파일·페이지·블록 및 내용 분류에 연결한다. 표는 전체 표를 보존하면서 열 제목을 붙인 행 단위로 검색용 청킹을 수행한다.
- 문서 분류: 본문, 회의록, 심의결과, 기타 첨부. 내용 분류: 안건, 결과, 보완 사유, 조건·기준, 안전성, 기능성, 참석 정보, 표, 기타. 내용은 복수 태그를 저장한다.
- 전체 활성 자료 또는 개별 문서를 `.md`로 다운로드한다. 목차, 출처, 파일·페이지 정보, 표, 원문, 청크와 임베딩 상태를 포함한다. 분류 다운로드는 해당 태그의 청크와 그 페이지를 포함한다.
- 검색은 활성 문서와 청크만 사용한다. 벡터 및 키워드 순위를 결합하고 답변 근거 카드에 실제 문서·페이지 링크를 제공한다.
- 실패·재시도·단계·페이지 위치를 DB 작업 테이블에 저장한다. 재구축이 실패해도 기존 활성 문서를 먼저 삭제하지 않는다.

현재 분류는 규칙 기반이다. OCR은 Gemini 시각 문서 처리 결과이며, 표 셀의 의미 정확도는 실제 자료에서 검토해야 한다. 페이지/블록 위치는 보존하며, 긴 토큰 입력을 추가 분할한 경우 문자 범위는 불확실성을 피하기 위해 비운다.

## 배포 전 필수 단계

1. 기존 DB의 복구 가능한 백업을 확보한다. 가능하면 검증용 DB/Preview부터 적용한다.
2. 현재 E5 `vector(384)` 스키마가 적용되어 있는지 확인한다.
3. **`prisma/committee_rag_v3.sql`을 적용한다.** 새 테이블과 청크 컬럼을 추가하는 마이그레이션이다. V3 코드가 새 컬럼을 조회하므로 SQL 적용 후 웹 앱을 배포한다.
4. 별도 E5 프로젝트(`services/e5-embedding`)를 업데이트한다. V3는 `strictTokens`와 `tokenCounts` 응답으로 입력이 512토큰을 넘지 않았는지 확인한다. 기존 E5 버전이면 V3 작업은 오류 사유를 남기고 대기/실패 처리된다.
5. 웹 앱을 배포한다. 기존 Gemini 키와 E5 연결 환경변수는 그대로 사용한다. 필요한 경우 OCR 모델만 별도 설정한다.
6. 관리 화면에서 개별 표본 문서를 처리하고 OCR 표·페이지·마크다운·검색을 검증한다.
7. 표본 검증 후 **전체 게시물 재수집 등록**을 실행하고 작업 실행기를 설정한다.

`committee_rag_e5.sql`은 기존 임베딩을 초기화하는 이전 전환용 SQL이다. V3 적용을 위해 다시 실행하지 않는다.

원본 PDF는 초기 구현에서 `committee_documents.original` BYTEA에 보관한다. 같은 파일을 재처리할 때 바이트 해시를 비교한다. 문서량이 커지면 원본은 객체 저장소로 이동할 수 있지만 현재 구현 DB 백업에 파일도 포함된다. 다운로드한 파일은 32MiB 한도이며 초과 파일은 자동으로 잘라 처리하지 않고 오류를 남긴다.

## Vercel에서 실행하는 방법

V3의 작업 상태는 DB에 있으며 실행 방법은 두 가지다. 로컬 서버를 새로 구성할 필요는 없다.

| 실행 방법 | 동작 |
|---|---|
| 관리자 `다음 작업 처리` | 로그인한 관리자가 `POST /api/committee/ingestion/tick`을 호출해 1개 단계/페이지를 처리한다. 진행 위치는 저장되지만 클릭 후 자동으로 나머지 모든 작업이 이어지지는 않는다. |
| 지속 실행 | 별도 worker에서 `npm run committee:worker`를 실행하거나, 스케줄러가 인증된 tick API를 주기적으로 호출한다. 이 방식으로 브라우저가 종료돼도 다음 작업이 처리된다. |

tick의 GET은 `Authorization: Bearer <CRON_SECRET>`을 요구한다. 환경변수 `CRON_SECRET`을 서버에 등록하고 스케줄러에서 같은 값을 사용한다. 인증되지 않은 요청은 401이다. POST는 동일 인증 또는 관리자 세션을 사용할 수 있다.

크론 설정은 자동 추가하지 않았다. 사용 중인 Vercel 요금제의 호출 간격과 실행 시간 한도를 확인한 후 `vercel.json`의 `crons`에 `/api/committee/ingestion/tick`을 등록하거나 외부 스케줄러를 연결한다. 한 호출은 1개 작업 단계를 수행하며 전체 백필의 속도는 호출 주기에 따라 달라진다. API의 최대 실행 시간 선언은 300초이며, 실제 호스팅 한도가 이를 지원해야 한다.

등록만 하고 호출하는 실행기가 없으면 대기 작업이 자동 처리되지 않는다. 이 안내는 관리 화면의 상태가 멈춰 보일 때 먼저 확인한다.

## 로컬 검증에 연결 설정이 필요한 경우

`.env.local`은 프로젝트 폴더의 비공개 설정 파일이다. PC에 DB나 AI 서버를 설치하는 파일이 아니다. Vercel에서 사용 중인 외부 서버 주소와 키를 PC에서 실행한 앱에도 알려준다.

| 변수 | 역할 |
|---|---|
| `POSTGRES_PRISMA_URL` | 현재 PostgreSQL 연결 문자열 |
| `POSTGRES_URL_NON_POOLING` | Prisma 직접 연결/관리 용도 문자열 |
| `GEMINI_API_KEY` | 현재 Gemini API 키 |
| `E5_EMBEDDING_URL` | 별도 E5 서버의 실제 임베딩 API 주소 |
| `E5_API_KEY` | E5 서버가 확인하는 Bearer 인증 키 |
| `GEMINI_OCR_MODEL` | 선택. OCR용 Gemini 모델. 미설정 시 `GEMINI_ANSWER_MODEL`, 그다음 코드 기본값 사용 |
| `CRON_SECRET` | 스케줄러에서 tick API를 호출할 때 사용 |
| `JWT_SECRET` | 관리자 세션 서명 검증. 해당 실행 환경의 로그인 설정과 일치해야 함 |

키를 채팅이나 Git에 올리지 않는다. `.env*`는 기존 `.gitignore`에서 제외된다. 로컬 연결을 사용하지 않으면 Vercel Preview에서 동일한 검증을 수행할 수 있다. 운영 DB 연결로 실행한 재수집·마이그레이션은 실제 운영 데이터를 수정한다.

## 검증 상태

- 프로덕션 빌드, Prisma 스키마 검증, 추가 파일 ESLint 검사 통과.
- 로컬 브라우저에서 자료실의 초기 화면을 확인했다. 기존 인증 정책으로 로그인 화면으로 이동하므로, 로그인 이후의 실제 다운로드·OCR 검토 조작은 연결 환경에서 검증해야 한다.

- Node 회귀 테스트: 청크 유실, 표의 행/열 대응, 복수 분류, 다운로드 원문 보존, 잘못된 PDF/OCR 응답 거부.
- PGlite(PostgreSQL) 테스트: 추가 SQL의 반복 적용, 기존 청크 유지, 작업 독점 획득, 임대 만료 재개, 재시도 시간, 활성 자료만 검색.
- 메모리의 12페이지 PDF를 11페이지에서 분리 처리하는 테스트. 이 테스트는 Gemini 응답을 대체하므로 실제 OCR 정확도 검증과 구분한다.
- 공개 식약처 제203차 상세 HTML로 본문 821자 및 HWPX/PDF 2개 첨부 탐색을 확인했다. 해당 HTML의 게시물 영역만 테스트 자료로 저장했다.
- 운영 DB의 실제 마이그레이션, Gemini OCR 및 E5 호출, 전수 백필은 아직 실행하지 않았다.

## 남은 검증 및 범위 제한

- 실제 한국어 PDF·표·스캔 문서 표본에서 OCR 결과를 원본과 대조한다.
- HWP/HWPX 등은 첨부 목록·미지원 상태를 남긴다. 형식 변환은 아직 구현하지 않았다.
- PDF에 있는 모든 안건을 구조화 테이블로 추출해 전체 목록/집계를 보장하는 작업은 남아 있다. 현재 검색 결과를 전체 건수로 해석해서는 안 된다.
- 생성 답변의 근거 ID 안내와 출처 카드가 있으며, 문장별 자동 검증 후 공개하는 별도 생성 후 검증기는 아직 구현하지 않았다.
- 삭제된 첨부파일을 자동 비활성화하는 정책은 확정하지 않았다. 새 버전 성공 시 이전 버전은 비활성화하며, 원본 접속 실패만으로 기존 근거를 지우지 않는다.
- 대규모 전체 다운로드·HNSW 성능·동시 사용자 성능은 운영 규모 표본으로 별도 측정한다.
